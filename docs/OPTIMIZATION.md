# Optimization Subsystem

## Overview and Purpose

The optimization subsystem wraps LLVM's optimization passes and provides a configurable optimization pipeline for Nitrate-compiled code. While the vast majority of optimizations are delegated to LLVM's mature and battle-tested pass infrastructure — which has been developed and refined over two decades of production use in Clang/LLVM — the optimization crate provides the integration layer between Nitrate's compilation pipeline and the LLVM optimizer, along with infrastructure for future Nitrate-specific optimization passes.

The purpose of optimization is to transform the generated LLVM IR into more efficient machine code without changing the program's observable behavior. Optimizations can reduce code size, improve execution speed, reduce memory usage, and enable further optimizations through canonicalization. The optimization level selected by the user (or build configuration) determines which transformations are applied and how aggressively.

## Architecture

**Crate**: `nitrate_optimization`  
**Key types**: `ModuleOptimizer`, `OptimizationPass` trait  
**Key files**: `src/optimization/src/lib.rs` (module definitions and optimizer), `src/optimization/src/traits.rs` (optimization pass traits)

## The ModuleOptimizer

The `ModuleOptimizer` is defined in the `nitrate_llvm` crate's `opt.rs`. It wraps an LLVM module and applies the standard LLVM optimization pipeline:

```rust
pub struct ModuleOptimizer<'ctx> {
    module: &'ctx Module<'ctx>,
    pass_manager: PassManager<Function<'ctx>>,
    // LLVM pass manager configuration
}

impl ModuleOptimizer {
    pub fn new(module: &Module, opt_level: u8) -> Self { ... }
    pub fn optimize(&self) { ... }
}
```

The optimizer is created with a reference to the LLVM module and an optimization level (0-3), then `optimize()` is called to run the appropriate passes.

## Optimization Levels

The compiler supports four optimization levels that correspond to LLVM's standard optimization levels:

| Level | Name       | LLVM Equivalent | Use Case                                                     |
| ----- | ---------- | --------------- | ------------------------------------------------------------ |
| 0     | None       | `-O0`           | Debug builds, fastest compilation, no optimization           |
| 1     | Less       | `-O1`           | Minimal optimization, quick compile feedback                 |
| 2     | Default    | `-O2`           | Standard optimization, good performance/compile-time balance |
| 3     | Aggressive | `-O3`           | Maximum optimization, release builds                         |

## LLVM Optimization Pipeline Details

When the optimization level is greater than 0, the `ModuleOptimizer` runs a subset of LLVM's standard pass pipeline. The actual passes applied are determined by LLVM's optimization pipeline builder, which selects passes based on the target architecture and optimization level.

### Level 1 (Basic - O1)

At this level, the optimizer focuses on cheap, predictable improvements:

- **Mem2Reg**: Promotes memory references (`alloca`/`load`/`store` sequences) to SSA registers. This is one of the most important LLVM passes because it converts the explicit stack-based representation generated by Nitrate's codegen into LLVM's native SSA form, enabling all subsequent SSA-based optimizations.
- **Instruction Combining**: Simplifies instruction patterns (e.g., turning `(x + 1) + 1` into `x + 2`, or eliminating redundant casts).
- **Dead Instruction Elimination**: Removes instructions whose results are never used.
- **CFG Simplification**: Merges basic blocks, eliminates unreachable code, and simplifies control flow.

### Level 2 (Standard - O2)

All Level 1 passes run, plus significantly more powerful optimizations:

- **Global Value Numbering (GVN)**: Eliminates redundant computations by detecting expressions that compute the same value. For example, if `a = x + y` and `b = x + y` appear in different parts of the function, GVN eliminates the second computation.
- **Sparse Conditional Constant Propagation (SCCP)**: Propagates constant values through the program, including through conditional branches. If a branch condition is determined to always be true, the false branch is eliminated.
- **Loop Invariant Code Motion**: Moves computations that produce the same result in every loop iteration to outside the loop.
- **Basic Inlining**: Inlines small functions at call sites, eliminating call overhead and enabling further optimizations.
- **Reassociation**: Reorganizes associative expressions (e.g., `(a + b) + c` → `a + (b + c)`) to enable better constant folding and CSE (Common Subexpression Elimination).

### Level 3 (Aggressive - O3)

All Level 2 passes run, plus aggressive and potentially size-increasing optimizations:

- **Function Inlining (Aggressive)**: Inlines functions more aggressively, including larger functions. This increases code size but can significantly improve performance by eliminating call overhead and enabling interprocedural optimization.
- **Loop Unrolling**: Unrolls loops with small trip counts to eliminate loop overhead and enable further optimizations on the unrolled body.
- **Vectorization (Loop and SLP)**: Transforms scalar operations into SIMD (Single Instruction, Multiple Data) vector operations. Loop vectorization processes consecutive loop iterations in parallel; SLP (Superword-Level Parallelism) vectorization groups independent scalar operations into vector operations.
- **Interprocedural Optimization**: Analyzes and optimizes across function boundaries, including argument promotion, constant propagation through call chains, and global variable optimization.
- **Profile-Guided Optimization**: When profile data is available (typically from a previous instrumented run), the optimizer uses branch frequency information to make better decisions about inlining, code placement, and loop transformations.

## Nitrate-Specific Optimization Infrastructure

The `nitrate_optimization` crate defines the `OptimizationPass` trait for future Nitrate-specific optimizations:

```rust
pub trait OptimizationPass<T> {
    fn optimize(&mut self, input: T) -> T;
}
```

This trait provides a standard interface for optimization passes that operate on HIR-level data or LLVM IR-level data. While all current optimization passes are delegated to LLVM, the trait infrastructure enables the development of Nitrate-specific passes that could perform:

### Planned Future Passes

- **Dead Generic Instantiation Elimination**: Analyzes the monomorphization cache and eliminates monomorphized copies that are never actually called. This reduces code bloat from generics.
- **Specialization of Common Generic Patterns**: Recognizes common generic instantiation patterns (e.g., `Vec<i32>`, `HashMap<String, ...>`) and applies optimized code generation strategies for these known patterns.
- **Constant Propagation for Refinement Types**: Tracks refinement type bounds through the optimization pipeline and eliminates runtime bounds checks when the compiler can prove they are unnecessary.
- **Trait Method Devirtualization**: When a call site's concrete type can be determined, replaces trait object method calls (dynamic dispatch through vtables) with direct function calls, enabling inlining and further optimization.
- **Custom Calling Convention Optimization**: Analyzes function call patterns and selects optimal calling conventions for internal functions.

## Integration into the Compilation Pipeline

Optimization runs after LLVM IR code generation and before object file emission:

```
Codegen → [LLVM Module] → [ModuleOptimizer] → [Optimized Module] → [Object/Assembly Output]
```

The integration flow:

1. **Code Generation**: `generate_llvmir()` produces a verified LLVM module
2. **Optimization Configuration**: The optimization level is read from `TranslationOptions::optimization_level`
3. **Optimizer Creation**: A `ModuleOptimizer` is created with the module and optimization level
4. **Optimization**: `optimizer.optimize()` runs the LLVM pass pipeline
5. **Output**: The optimized module is emitted as an object file, assembly file, or LLVM IR text

## Performance Impact

The optimization level significantly affects both compile time and code quality:

- **Level 0**: Fastest compilation, minimal debugging interference (no optimizations reorder or eliminate code), but the generated code is unoptimized with many redundant loads/stores.
- **Level 1**: ~2-3x compilation time vs level 0, provides basic improvements without aggressive transformations.
- **Level 2**: ~5-10x compilation time vs level 0, provides near-maximum performance for most code. This is the recommended level for release builds unless maximum performance is required.
- **Level 3**: ~10-20x compilation time vs level 0, may increase code size through aggressive inlining and loop unrolling. Only recommended for compute-intensive code where every percentage point of performance matters.
